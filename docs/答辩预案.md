## 三、高频问题标准答案（25 个，覆盖所有技术点）

### 🔹 数据层

**Q1：数据是真实的豆瓣数据吗？**  
A：真实豆瓣 API 有反爬限制，我们用 Python 做了**真实数据优先 + 本地模拟 fallback** 的方案：脚本会先尝试从 Kaggle TMDB 下载公开的 5000 部电影数据集（有 GitHub 镜像），如果下载成功就能解析成我们的字段格式；为了保证可复现和离线可用，fallback 是我们用 `random.seed(42)` 生成的 850 条高质量数据——电影名、导演、演员都是从真实名单里抽的组合，评分符合正态分布 N(7.0, 1.2)，国家和类型有合理的概率偏置，预算和票房有约 50% 覆盖。

**Q2：为什么是 850 条，不是 1000 或 5000？**  
A：850 是我们权衡了几个因素定的——太少（比如 200）图表稀疏看不出趋势，太多（比如 5000）数据库冷启动与图表渲染都会明显变慢。850 刚好让每张图表每个 bin 里至少有 5–10 条数据点，曲线平滑。如果后续要加真实数据，生成脚本里只改一个参数 `n=` 就能扩。

**Q3：评分为什么用正态分布 N(7.0, 1.2)？**  
A：真实豆瓣评分的整体均值就在 7.0 左右，标准差约 1.2，呈现"中间多两头少"的分布——2 分以下和 9 分以上都是长尾。我们在这个基础上给不同类型加了偏置：动画、纪录片、文艺片整体偏高（+0.4 ~ +0.6），恐怖片偏低（-0.3），这样更接近真实豆瓣上的类型口碑分布。

**Q4：档期是怎么标注的？**  
A：根据 `release_date` 的月份自动打标签：12-1月→贺岁/春节档，7-8月→暑期档，10月→国庆档，5月→五一档，11月→圣诞档，其余→淡季。另外加了规则：主旋律/战争片 60% 概率强制归到国庆档，动画 50% 概率归暑期或圣诞——这都是真实国产电影市场的规律。

**Q5：为什么约 50% 的电影有财务数据？**  
A：真实世界里只有院线电影、有公开数据的头部电影才会公开预算和票房。文艺片、短片、小成本独立电影大概率没有公开财务数据。所以我们在生成脚本里用概率控制是否带财务信息；当前入库的 850 条数据均带完整财务字段。前端散点图、档期图、成本效益图都会自动过滤掉没有财务数据的条目。

### 🔹 后端架构

**Q6：为什么用 MySQL 而不是 H2 之类的内嵌数据库？**  
A：三个原因——① 课程要求数据必须真实入库，MySQL 是生产级关系数据库，答辩时可以现场用 Workbench 跑 `SELECT COUNT(*) FROM movies` 验证数据真实存在；② MySQL 支持索引、复杂 JOIN 和事务，为后续扩展留出空间；③ 通过环境变量注入数据源，换机器/换账号只需改配置或设置环境变量，Java 代码完全不用动——Spring Boot 的抽象已经做到了。

**Q7：前后端怎么通信？跨域怎么解决的？**  
A：前端用原生 `fetch` API，后端是 Spring Boot REST Controller。跨域有两层保障：① 部署时前端静态资源和 API 都由 Nginx 在 80 端口统一提供（`/api/` 反向代理到 8081），浏览器视角是同源请求，根本不产生跨域；② 后端额外保留全局 `CorsConfig`，方便绕过 Nginx 直连 8081 调试。另外如果老师问为什么不用 Spring Security——因为这是纯前端演示项目，不需要登录鉴权。

**Q8：`Result<T>` 统一返回格式是为什么？**  
A：三个好处——① 前端拦截逻辑统一，`if (res.code !== 0) showToast(res.message)` 一处搞定所有错误提示；② 接口文档（ApiFox 导入的 OpenAPI JSON）可以据此生成标准结构；③ 避免每个接口各用各的返回格式（有的用 Map，有的直接返回对象，有的包一层 "success": true）。我们工厂方法提供了 `Result.ok(data)` / `Result.error(msg)` 一行能用。

**Q9：Entity 和 DTO 为什么要分开？**  
A：Entity 是数据库表的直接映射，DTO 是接口出入参的契约——两者分开的好处：① 数据库字段改动（比如 movies 表加一列 intro）不影响前端 DTO；② 前端列表页只需要精简字段（id/title/rating），详情页才需要完整字段和类型列表，一个 Entity 塞不下也不该塞；③ 多表聚合时（比如详情要带财务数据）DTO 可以内嵌静态类组合，Entity 做不到。

**Q10：Repository 层都做了什么？**  
A：用 Spring Data JPA，三个 Repository 接口继承 `JpaRepository`。核心是 `MovieRepository.findByMultiCriteria()`——手写 JPQL，用 `(:param IS NULL OR 条件)` 模式实现动态筛选，`LEFT JOIN FETCH m.genres` 一次带回类型避免 N+1，并配了独立的 `countQuery` 保证分页总数准确；筛选器选项用 `@Query("SELECT DISTINCT m.year FROM Movie m ...")`；另外保留了 `findByTitleContaining` 等命名查询。MovieFinancialRepository 做 `findByMovieId`；GenreRepository 做 `findAll()` / `findByName()`。

**Q11：分页参数是哪来的？怎么实现的？**  
A：前端传 `page`（从 0 开始）和 `size`（默认 20），后端用 Spring Data 的 `PageRequest.of(page, size)` 创建分页对象，Repository 返回 `Page<Movie>`，Spring Boot 自动转成 JSON 包含 `content` / `totalElements` / `totalPages` / `number` / `size`。前端读 `data.totalPages` 渲染上一页/下一页按钮。

**Q12：接口文档是怎么管理/调试的？**  
A：我们用 ApiFox 管理接口（替代 Swagger UI）。仓库里的 `docs/apifox-import.json` 是标准 OpenAPI 3.0 文件，ApiFox 里「导入 → OpenAPI/Swagger → 选文件」即可一键生成 9 个带参数说明和响应示例的接口，还能保存不同环境的 base URL 直接调试。这样做的好处是：不引入额外依赖，文档文件随代码版本管理，团队协作时大家导入同一份文件即可。

**Q13：筛选条件里多个 genres 参数是 AND 还是 OR？**  
A：是 AND——我们用 `List<String> genres` 接收多个重复参数（`?genres=科幻&genres=动作`），Service 里写的是 "同时包含所有选中的类型"。比如用户选了"科幻+动作"，返回的是 **既是科幻又是动作** 的电影（如《盗梦空间》），不是"科幻或动作"。这样结果更精准。

### 🔹 前端

**Q14：为什么不用 Vue/React，要用原生 JS？**  
A：这是 Web 前端课程作业，老师希望看到原生能力的掌握——HTML/CSS/JS 的核心概念、DOM 操作、事件模型、fetch API、ES6+ 语法（let/const / 箭头函数 / 解构 / 模板字符串 / Promise）。如果用 Vue/React，构建工具的使用、组件库的调库可能会掩盖原生能力的掌握。另外我们零构建部署：Nginx 直接托管静态目录，一条 `nginx.exe` 就能把项目跑起来，工程链路更短更可控。

**Q15：ECharts 主题切换怎么实现的？**  
A：CSS 变量 + chart.setOption() 重载。步骤：① CSS 里定义 `:root { --bg: #ffffff; --text: #333 }` 和 `body.dark { --bg: #1a1a1a; --text: #eee }`；② 切换按钮点击时给 body 加/移除 `dark` 类；③ 每个图表的 init() 时读当前 CSS var，切换时调用 `chart.dispose()` + `echarts.init(container, theme, { renderer: 'canvas' })` 重新初始化。或者更轻量——只改 `chart.setOption({ textStyle: { color: getComputedStyle(document.body).getPropertyValue('--text') } })`。

**Q16：筛选条实时联动会不会频繁请求？**  
A：我们做了防抖——每个输入框的 change/input 事件绑定的是 `debounce(doFilter, 300)`，意思是用户停止输入 300ms 后才真正发请求。所以连续拖动年份滑块不会一秒发 10 个请求。另外我们每次发的是全量参数刷新（所有筛选条件一起传给后端），不是每个条件单独传。

**Q17：8 张图表都要各自写一次 fetch 吗？**  
A：不是。我们把 API 调用都封装在 `utils/api.js` 里：`window.API.get(path, params)` 统一拼 URL、校验 `code`、带 8 秒超时和 localStorage 缓存。`config.js` 里 `API_BASE: ''`，请求全部走 Nginx 同源代理。main.js 里定义了一个统一的 `reloadAll()` 函数，`Promise.all` 并发 7 个接口（movies + 6 个 stats），每个 resolve 后调对应的 render 函数；其中成本效益和桑基图是前端基于前两个接口的数据二次加工，不额外发请求。

**Q18：电影详情弹窗是怎么实现的？**  
A：纯 DOM + CSS，没有用任何 UI 库。HTML 里放一个 `<div id="modalOverlay" hidden>`，点击卡片时 → fetch `/movies/{id}` → 生成 innerHTML → `modalOverlay.removeAttribute('hidden')`。关闭方式有三种：① 右上角 × 按钮；② 点击遮罩层（事件绑在 overlay 上，不绑在 modal 上，这样点 modal 内部不会关）；③ ESC 键（keydown 监听）。

**Q19：KPI 卡片的数据是怎么来的？**  
A：两种方式——① 简单的（总数、覆盖国家）：直接查 `/api/movies` 默认分页，然后前端遍历所有内容算 count 和 country Set size；② 更高效的：其实我们可以在后端加一个 `/api/stats/summary` 接口一次性返回所有 KPI，但课程作业量有限，前端算也很快（数据量只有 850 条）。

### 🔹 工程与设计

**Q20：如果让你再加一个"推荐算法"功能，应该在哪改？**  
A：① Controller 加一个 `GET /api/recommend/{movieId}`；② Service 里实现余弦相似度或基于内容的推荐（看哪些用户看过同类型+同国家+评分接近的电影）；③ Entity 层其实现在没有 User 和 Rating 表，要加的话在 schema.sql 里加两张表；④ 前端在详情弹窗底部加"相关推荐"区块。

**Q21：如果数据量扩大到 100 万条怎么办？**  
A：我们当前的设计有几个天然瓶颈——统计是 Java 内存分组（全量捞取再分组）、多类型筛选要内存补齐、前端一次渲染 850 个图表点。扩大的话：① 统计改 `@Query` 原生 SQL `GROUP BY` 下推数据库，或引入物化视图；② 加 Redis 缓存热点查询；③ Repository 的查询已带索引（`release_year` / `rating` / `country`），可再评估联合索引；④ 前端散点图用 ECharts dataset + large 模式或 WebGL；⑤ 筛选联动保持 debounce + 后端异步。

**Q22：代码行数大概多少？**  
A：后端约 2000 行（Entity/DTO/Service/Controller 平均每个 150–300 行），前端约 1500 行（HTML 200、CSS 400、JS 900），Python 脚本约 700 行。加起来约 4200 行。

**Q23：如果用 Docker 一键打包能做到吗？**  
A：可以。后端写一个 Dockerfile（`FROM eclipse-temurin:17-jre` → `COPY target/*.jar app.jar` → `EXPOSE 8081` → `ENTRYPOINT java -jar app.jar`），前端用 nginx 镜像，docker-compose.yml 把 MySQL + 后端 + Nginx 三个服务连起来，MySQL 用命名卷持久化数据。这样老师 `docker-compose up` 就能直接跑。当前交付用的是本机三件套手动部署（见 `docs/快速上手.md`），容器化列为后续优化项。

**Q24：前后端没启动会怎样？**  
A：前端 api.js 里做了错误处理——fetch 失败或 `response.code !== 0` 时调用 `showToast('数据加载失败，请确认后端已启动')`，图表容器显示占位文字"暂无数据"。不会出现白屏。

**Q25：你们用 AI 辅助写代码了吗？**  
A：用了。具体每个文件的 AI 使用情况如实记录在 `docs/AI使用记录表.md`。总体策略是：后端骨架（pom.xml 依赖、Entity/DTO 模板、Controller 注解）让 AI 生成初稿，Service 层的业务逻辑（复杂 JPQL、筛选组合、统计聚合）自己写；前端 ECharts 配置项让 AI 辅助调参，布局和样式自己写；Python 数据生成器自己写的（因为要精确控制分布特征）。**我们的原则是——AI 帮我们减少重复劳动和查文档的时间，但每个关键逻辑都要自己读懂和修改。**

## 四、紧急情况预案

| 情况                                              | 应对                                                                                  |
|---------------------------------------------------|---------------------------------------------------------------------------------------|
| ❌ 后端启动报错（端口被占 / Java 版本不对）        | ① 提前装好 Java 17 并验证；② 端口占用：`netstat -ano \| findstr :8081` 查 PID → taskkill；③ 备用方案：提前录好演示视频/截图 |
| ❌ ApiFox 导入/调不通                              | 导入时选 OpenAPI/Swagger 并指定 `docs/apifox-import.json`；调不通先确认后端在 8081 运行，且环境里的 base URL 与实际端口一致 |
| ❌ 浏览器不兼容 ECharts                            | 提前用 Chrome 或 Edge 演示（别用 Safari 或 IE）                                       |
| ❌ 前端 fetch 报 CORS                              | 生产走 Nginx 同源不应出现；若直连 8081 调试，检查 CorsConfig 的 allowedOriginPatterns    |
| ❌ 图表一片空白 / "暂无数据"                        | 打开 F12 Console 看 fetch 返回了什么；如果库里没数据，TRUNCATE movies + movie_financials 后重启后端，让 DataInitializer 重新加载 CSV |
| ❌ 筛选条件改了没反应                              | 检查是不是忘记重新启动后端（改了 application.yml 或 Java 代码要重启）；或检查前端 debounce 有没有触发 |
| ❌ 网络挂了（需要联网打开 ECharts CDN）            | **提前离线缓存**——把 `echarts.min.js` 下载到 `frontend/vendor/` 目录，改 index.html 的 script src |
| ❌ 忘带电脑 / 电脑没电                             | 提前用 U 盘拷一份完整项目 + 录屏；问老师能不能用现场机器                               |
| ❌ 老师突然说"别演示了，直接讲设计"                 | 重点讲：① 三层架构的分层思想；② 数据生成的质量控制；③ Entity/DTO 分离的理由；④ 零配置部署的设计决策 |
