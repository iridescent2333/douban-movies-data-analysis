# 团队协作指南（GitHub）

> 给谁看的：三位组员 + 组长（仓库发起人）
> 阅读指引：**组长先看第 1、2 节完成仓库设置**；全员看完第 3–7 节再动手写代码；日常开发只重复「第 4 节的一个迭代」。
> 本文件是团队协作的**唯一权威规范**，与 `组员任务清单.md`（任务分派）配合使用。

---

## 一、组长必做：仓库初始化清单（一次性）

仓库地址：<https://github.com/iridescent2333/douban-movies-data-analysis>

### 1.1 邀请另外两位成员

1. 仓库页面 → **Settings** → **Collaborators** → **Add people**
2. 输入对方的 GitHub 用户名（先问清楚，不是邮箱也不是真名）
3. 权限角色选 **Write**（可推送分支、开 PR、管理 Issue；不能改设置、不能删仓库）
4. 对方邮箱会收到邀请链接，**24 小时内有效**，过期需重发

> ⚠️ 只有「直接 push 到 main」这一项是 Write 权限默认允许的——所以必须配合下一步的分支保护，否则邀请等于把 main 敞开。

### 1.2 配置 main 分支保护（核心！）

Settings → **Branches** → **Add branch ruleset / Add classic rule**，分支名模式填 `main`，勾选：

| 规则 | 作用 |
|------|------|
| ✅ Require a pull request before merging | 任何人不能直接 push main，必须走 PR |
| ✅ Require approvals：1 人 | 至少 1 位其他组员 review 通过才能合 |
| ✅ Require conversation resolution | PR 上的 review 意见必须全部处理完才能合 |
| ✅ Do not allow force pushes | 禁止强推覆盖历史 |
| ✅ Do not allow deletions | 禁止删除 main |

### 1.3 其他建议设置

| 设置 | 位置 | 建议 |
|------|------|------|
| Discussions 开启 | Settings → General → Features | 组内异步讨论、答辩提问收集 |
| Issues 开启 | Settings → General → Features | 任务分派与缺陷跟踪 |
| Projects 看板 | Projects → New project（Board 模板） | 建「看板/待办/进行中/待review/已完成」五列 |
| 默认分支保持 main | Settings → General → Default branch | 不要改成 master |
| Tag 锁定版本 | Releases → Create a new tag | 答辩前打 `v1.0`，固定"可交付版本" |

### 1.4 仓库已有协作资产（本目录下）

| 文件 | 用途 |
|------|------|
| `CONTRIBUTING.md`（根目录） | 贡献指南入口，GitHub 会在新建 PR/Issue 时自动提示 |
| `.github/CODEOWNERS` | 按目录自动分派 review 人 |
| `.github/PULL_REQUEST_TEMPLATE.md` | PR 必填检查单 |
| `.github/ISSUE_TEMPLATE/` | Bug 报告 / 需求提案两个模板 |

## 二、分支模型（三人小团队，从简）

```
main          ──●──────────●──────────●────── 受保护，只接受 PR 合入；每个 ● 都是可运行版本
               ▲          ▲
                 │          │
feature/xxx    ──┴──────────┘          每人领了任务从最新 main 切出，完成后 PR 回 main
```

| 分支 | 命名 | 谁能动 | 说明 |
|------|------|--------|------|
| `main` | `main` | 只能 PR 合入 | 保持随时能跑；对外交付/答辩以 main 为准 |
| 功能分支 | `feature/后端-接口`、`feature/前端-图表`、`feature/文档-契约更新` | 认领人自己 | 一个分支只干一件事，做完即删 |
| 修复分支 | `fix/登录页样式错位` | 认领人自己 | 紧急 bug 修复，流程同 feature |

**禁止**：三个人同时在同一个分支上推来推去；禁止把 `main` 直接改坏了再修。

```bash
# 每天开工第一件事：同步主仓最新代码
git checkout main
git pull origin main
git checkout -b feature/你的任务名   # 从最新 main 切分支
```

## 三、Commit 规范（已有，全员遵守）

格式：`类型(范围): 一句话说明`，一句话说清"做了什么"，正文可选。

| 类型 | 用途 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(backend): 新增 /api/stats/box-office-live 实时票房接口` |
| `fix` | 修 bug | `fix(frontend): 修复暗色主题下 tooltip 文字不可见` |
| `docs` | 文档/注释 | `docs: 校准 API 契约中 movies 表列名 release_year` |
| `refactor` | 重构（不改行为） | `refactor(backend): StatsService 提取公共 filterMovies` |
| `style` | 格式调整（不影响逻辑） | `style: 统一缩进为 4 空格` |
| `test` | 测试相关 | `test(backend): 补充 MovieService 多类型筛选用例` |
| `chore` | 构建/工程/杂项 | `chore: 更新 .gitignore 排除 logs 目录` |

**范围**用模块名：`backend` / `frontend` / `scripts` / `docs` / `repo`。

**提交粒度**：一个 commit 只做一件事。别把「改后端 + 改前端 + 顺手改文档」搓成一个巨大 commit——review 的人会疯。

## 四、日常开发流程（一个迭代的完整循环）

```
① 认领任务（Issue / 看板）
      ↓
② git pull origin main → 切 feature 分支
      ↓
③ 写代码 + 本地自测（后端能起、页面能开、接口 curl 过一遍）
      ↓
④ commit（规范信息）→ push 到自己的 feature 分支
      ↓
⑤ 开 Pull Request → 填 PR 模板检查单 → 指定 review 人（CODEOWNERS 会自动指派）
      ↓
⑥ review 意见处理（讨论 + 修改 + 再 push，PR 会自动更新）
      ↓
⑦ 至少 1 人 Approve → Squash / Merge 合入 main → 删掉 feature 分支
```

### 4.1 开 PR 的操作

```bash
git push -u origin feature/你的任务名
# push 后终端会返回一个 PR 创建链接，点开即可；或在仓库首页点 Compare & pull request
```

PR 标题同样遵守 commit 规范，例如：`feat(frontend): 电影详情弹窗新增收藏按钮`。

### 4.2 PR 合并前必须自测（写在模板里，靠自觉 + review 人把关）

- [ ] 后端 `mvnw.cmd spring-boot:run` 能正常启动，控制台有 `[DataInit] 加载完成！`
- [ ] 涉及接口的：ApiFox 或 curl 实际调过，返回 `code:0`
- [ ] 涉及页面的：浏览器打开看板无 Console 报错，明暗主题都看过
- [ ] 涉及数据的：`scripts/generate_data.py` 重跑结果一致（种子 42）
- [ ] 没有把 `application-local.yml` / `.env` / 任何真实密码提交进来
- [ ] 改了接口/数据库/配置：同步更新 `docs/` 下对应文档（契约文档是团队的"法律"）

### 4.3 Review 别人代码时看什么

| 维度 | 检查点 |
|------|--------|
| 功能 | 是否真的实现了 Issue 描述的需求，有没有顺手机坏别的功能 |
| 契约 | 接口入参/出参、数据库字段是否与 `docs/数据库与API契约.md` 一致 |
| 安全 | 有无硬编码密码、有无把堆栈返回给前端 |
| 规范 | commit 信息、分支命名、注释是否为中文、是否违反分层调用（Controller→Service→Repository 单向） |
| 文档 | 代码改了行为，文档改了没有 |

> Review 意见写具体点：❌「这里不对」✅「`loadMovieList()` 里页码忘了 -1，第 2 页会重复第 1 页数据，见 docs/代码说明.md 4.4」。

## 五、Issue 与看板（任务分派与进度透明）

| 场景 | 用具 |
|------|------|
| 领到新任务 | 组长建 Issue（选「需求提案」模板），Assignees 指派负责人，Labels 标 `backend`/`frontend`/`docs`/`bug` |
| 开发中 | Issue 里更新进度；卡壳了在 Issue 下评论或群里 @组长 |
| 做完了 | PR 描述里写 `Closes #Issue编号`，合并后 Issue 自动关闭 |
| 发现 bug | 谁发现谁建 Issue（选「缺陷报告」模板），能复现步骤 + 截图 |
| 每周同步 | 看板过一遍：待办 → 进行中 → 待 review → 已完成 |

## 六、容易踩的协作坑（血泪预防）

| 坑 | 预防 |
|----|------|
| 组员 clone 后**没有 Nginx**（`frontend/nginx-1.26.2/` 被 .gitignore 排除，二进制不入库） | 按 `docs/快速上手.md` 自行下载 Nginx 或用 `docs/nginx.conf.example` 配置 |
| 组员 clone 后**后端连不上数据库** | 复制 `application-local.yml.example` 填自己的密码，**该文件不入库，各填各的** |
| 手滑把含密码的 `application-local.yml` 提交了 | `.gitignore` 已拦截；万一只手滑 `git add -f`，立即告诉组长改密码并强制清理历史 |
| 两个人同时改同一个文件（如 `main.js`） | 认领时就说清楚谁改哪块；冲突了面对面一起合，别瞎猜 |
| PR 里混进无关改动 | 一个分支只干一件事；提交前 `git diff main` 自查一遍 |
| 接口改了前端不知道 | 改接口的人**必须**在同 PR 里更新 `docs/数据库与API契约.md` 和 `docs/apifox-import.json`，并群里通知 |
| CSV 数据变了但库里还是旧的 | DataInitializer 只在表为空时加载；TRUNCATE 两张表再重启（见 `docs/快速上手.md` FAQ） |

## 七、协作节奏（与组员任务清单联动）

| 时间 | 动作 |
|------|------|
| 每天开工 | `git pull origin main`，同步队友进度 |
| 周三晚 | 各自把进行中的分支合 PR；跑一遍端到端（MySQL→后端→Nginx→看板） |
| 周日晚 | 15 分钟语音：进度、卡壳点、下周认领 |
| 答辩前 3 天 | 打 `v1.0` tag 锁定版本；全量打包到答辩电脑实测 |
| 答辩前 1 天 | 彩排 2 次（见 `docs/答辩预案.md`） |

## 八、Git 命令速查（给忘了的同学）

```bash
# 同步主仓
git checkout main && git pull origin main

# 开新分支
git checkout -b feature/任务名

# 看看改了啥 / 暂存 / 提交
git status
git diff                 # 未暂存的改动
git diff --staged        # 已暂存的改动
git add backend/src/     # 只暂存该目录，别一把 git add .
git commit -m "feat(backend): xxx"

# 推送并建 PR
git push -u origin feature/任务名

# 分支名起错了 / 还没 push，重命名
git branch -m feature/新名字

# 放弃某个文件的本地修改（危险！改没了）
git checkout -- 文件路径

# PR 被要求修改：继续在新分支上 commit + push，PR 自动更新
```

> 拿不准的命令先问，**`push --force`、`reset --hard` 在共享分支上永远别用**。
